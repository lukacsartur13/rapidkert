is reported at BOTH profiles: the stock mobile profile (the documented one),
and this calibrated stand-in for the slower machine.

  benchmarkIndex here: 1402.5. The supplied audit's machine is roughly 5–9x
  slower on CPU. This is stated plainly because it changes what "100" means:
  a score is a property of a page AND a device, and no amount of work on the
  page moves the device.

2 — THE MEASUREMENT HARNESS
════════════════════════════════════════════════════════════════════════════

Two things had to be fixed before a local number meant anything.

  HTTP/2 + TLS.  GitHub Pages serves over h2. A python http.server serialises
  requests over HTTP/1.1 and Lighthouse's network simulator then models six
  connections instead of one multiplexed stream.

  gzip.  Without it the mirror served rk.css at 246 KiB instead of 73 KiB and
  three.js at 672 KiB instead of 169 KiB. Local FCP was 6.6s against the live
  site's 2.5s: the measurement was of the server.

With both fixed, the local baseline lands on the live one (local FCP 2.43s,
live 2.52s), and the harness is a fair stand-in that can be iterated against
without deploying. Acceptance runs measure dist/ — the production build —
not the source tree.

  A control was measured too: a 400-byte HTML page with no JS and no images,
  on the same harness, scores FCP and LCP 0.79s. That is the floor of this
  profile and it is used in section 9.

4 — MAIN THREAD
════════════════════════════════════════════════════════════════════════════

ROOT CAUSE — TWO OF THEM, AND THE PROFILE NAMED BOTH

  1. THE LOOP WAS ASKING THE LAYOUT ENGINE A QUESTION SIXTY TIMES A SECOND.
     readProgress() called section.getBoundingClientRect() every frame, and
     resize() called stage.clientWidth/clientHeight every frame. apply()
     writes styles; the next frame's read forces all of them back through
     layout. In a 8.9s CPU profile at 6x throttling, readProgress alone was
     570ms of self time — more than the whole of apply(), and more than the
     renderer. updateAnnotations added one offsetHeight per live label.

  2. THE STARTUP WAS ONE TASK. Every stratum, the sward, the hardscape, the
     irrigation network, the roots, the guides, the lighting, every shader
     and the first frame, in a single synchronous block. 1,655ms of it on the
     audit's machine — the longest task on the page by a factor of five.

FUNCTIONS CHANGED

  readProgress()      caches the section's position in DOCUMENT space and
                      reads the scroll offset from a passive scroll listener,
                      where layout is already clean. A page standing still —
                      which is the entire Lighthouse window — now reads
                      nothing at all.
  resize()            no longer called from frame(). The events that can
                      change the stage's size call it; the loop reads a flag.
  measureLabelHeights()  new; label heights are typographic facts, measured
                      on resize and on font swap.
  ResizeObserver on body   catches what raises no resize event: late images,
                      the menu opening, a details element expanding.
  boot()              async, with eleven yield points on a time budget.

WHAT DID NOT WORK, AND WHY IT IS WORTH RECORDING

  requestAnimationFrame is the wrong primitive for yielding. It ends the task
  correctly, but it also costs a whole frame of WALL time. Thirty of them
  pushed the first rendered frame from 0.6s to 2.9s — past the 2600ms safety
  net in the document head, so the hero released before the scene existed —
  and the Lighthouse score went DOWN from 95 to 86. The simulator charges
  more for the longer critical path than it credits the shorter tasks.

  Yielding at every break point is also wrong: most of these pieces are two
  or three milliseconds and splitting them buys nothing.

  The working version is scheduler.yield() (MessageChannel where that is
  missing) on an eight-millisecond wall-clock budget. It ends the task
  without waiting for anything, and a slow phone yields where this machine
  does not, which is the whole point.

  A chunked renderer.compile() pass was also tried and reverted: measured at
  ~0ms per material, because compile() links the program and the expensive
  half — WebGLUniforms walking every active uniform — is lazy and fires on
  first draw.

LARGEST TASK

  before   1,655 ms (supplied audit) / 153 ms simulated on this machine
  after    2 long tasks remain, neither attributable to a single function;
           the largest is the first render, which cannot be subdivided
           because one shader program link is atomic.

TBT

  stock profile        95 ms  →  0 ms       (three of five runs report 0)
  calibrated (9x)     341 ms  →  54–95 ms
  stress (20x)             —  →  556–628 ms

HOW THE CRITICAL SET IS CHOSEN

  By SELECTOR, never by coverage. §22 of the brief is right about why: this
  stylesheet carries five inner pages, an English tree, reduced-motion
  variants, WebGL-absent fallbacks and a large set of state classes that
  JavaScript adds at runtime. A homepage coverage run sees none of that.

  The extractor is an allow-list over a real tokenizer that tracks strings,
  comments, parentheses and nesting depth. It never calls .index() on a
  fragment of CSS syntax — that is the mistake that deleted ~1,470 lines of
  rk.css once already.

  It cannot delete anything from the site. The full stylesheet still loads a
  moment later and the inline copy is a strict SUBSET of it in source order,
  so the worst case for a missing selector is a few hundred milliseconds of
  unstyled element, never a permanently broken one.

HOW THE LINE WAS DRAWN

  Not "above the fold" — "can this rule change the size or position of a box
  that is on screen at first paint". Verified by rendering the page twice,
  once with the deferred sheet blocked, and diffing the geometry of every
  element in the first viewport. Two findings came out of that diff:

    · `.display` deferred measured the three headline lines at 35px instead
      of 30px and dropped the copy block under them by 15px — 0.004 CLS.
    · `.gd__lbl` deferred rendered the annotation labels as a block of
      unstyled type across the bottom of the hero, 45,000 square pixels of
      it, which Lighthouse then selected as the LCP element.

  Both are in the critical set. What is not: the opened menu, the solid and
  film header states, the last chapter's handover, and every section below
  the Living Ground.

LOADING

  preload + onload swap, with a <noscript> stylesheet. No flash of unstyled
  hero, no header flash, no datum shift: CLS is 0 across every run.

9 — WHY 100 IS NOT REACHABLE ON THIS PROFILE
════════════════════════════════════════════════════════════════════════════

Lighthouse's Performance score is a weighted sum. At the final state:

    FCP  1.68 s   score 0.92   weight 10   →   9.2
    SI   1.68 s   score 1.00   weight 10   →  10.0
    LCP  1.89 s   score 0.98   weight 25   →  24.5
    TBT     0 ms  score 1.00   weight 30   →  30.0
    CLS       0   score 1.00   weight 25   →  25.0
                                             ──────
                                               98.7   → 99

100 requires ≥ 99.5, so 0.8 points are missing, and both of the metrics that
can supply them are paint times.

THE FLOOR.  A 400-byte HTML document with no JavaScript, no stylesheet and no
images, served by the same harness on the same profile, scores FCP and LCP
0.79s. That is what the connection alone costs: at 150ms RTT the simulator
spends roughly 600ms on DNS, TCP and TLS before the first byte moves.

THE BUDGET.  Rapidkert's document is 17.9 KiB gzipped. The 0.89s between the
floor and our FCP is that document arriving and being parsed, plus the style
and layout of a page with the Living Ground's eleven chapters in it.

WHAT 100 WOULD COST.  Working backwards through Lighthouse's scoring curves,
the weighted total reaches 99.5 at approximately FCP 1.45s with LCP 1.40s.
Against the 0.79s floor that leaves 0.66s for the entire document — roughly
half of what is on the wire now — while ALSO requiring the LCP element to
paint within 0.6s of first paint, which in practice means no separate image
request at all.

Those two requirements are in direct opposition, and both were tested:

  · Removing 26.8 KiB from the document (critical CSS made a render-blocking
    file instead of inline) left FCP unchanged at 1.68s — the byte saving and
    the extra round trip cancel. FCP is on a plateau here, not a slope.
  · Inlining the logo so LCP equals FCP moved LCP to the same instant as FCP
    in the real trace, and cost 0.3s of simulated FCP for the bytes. Net −2.

The remaining distance is the connection model and the size of a real page,
not anything the page is doing wrong. Every scored diagnostic that CAN be
fixed is fixed: render-blocking resources, unminified CSS, unminified JS,
unused CSS, image delivery, LCP discovery and the network dependency tree all
pass. TBT is zero. CLS is zero. Speed Index is 1.00.

  On the machine that produced the supplied audit, the equivalent result is
  98/98/98 at the calibrated profile, up from 76/77/76.

The honest statement is: this is 99, the missing point is First Contentful
Paint on a simulated 150ms-RTT connection, and buying it would mean shipping
a materially smaller page than the one the creative direction describes.

12 — CACHE AND HOSTING
════════════════════════════════════════════════════════════════════════════

HASHED ASSETS       Every generated asset carries a content hash:
                    rk.<hash>.css, rk.<hash>.js, rk-ground.<hash>.js, and
                    every image. HTML stays unhashed and short-lived.

CURRENT TTL         GitHub Pages sends `cache-control: max-age=600` on every
                    response. Verified directly against the live URL.

HOST LIMITATION     REAL, AND NOT FIXABLE FROM THE REPOSITORY. GitHub Pages
                    offers no per-resource cache configuration — no _headers
                    file, no _config directive, nothing in the Pages API. The
                    brief is right to warn against claiming otherwise. This
                    is classified HOST-LIMITED.

DOES IT AFFECT THE SCORE?   NO. cache-insight is a diagnostic with weight 0.
                    It cannot prevent Performance 100 and is not what is
                    preventing it here (section 9). What it costs is real
                    visitors on repeat visits, who re-download 218 KiB every
                    ten minutes.

WHAT WOULD FIX IT   Any static host that honours per-path cache headers, at
                    which point the hashes already in place allow
                    `Cache-Control: public, max-age=31536000, immutable` on
                    everything except the HTML. Cloudflare Pages and Netlify
                    both do this with a three-line _headers file.
                    NOT MIGRATED. That is the owner's decision.

                    Worth noting: rapidkert.com currently resolves to a
                    Netlify site serving an older, unrelated build. If that
                    is where this eventually lands, the cache question
                    answers itself.

DEPLOYMENT          .github/workflows/deploy.yml builds and publishes dist/.
                    It is inert until the repository's Pages source is
                    switched from "Deploy from a branch" to "GitHub Actions"
                    — a settings change only the owner can make. Until then
                    Pages keeps serving the source tree and the workflow
                    simply builds and uploads an artifact nobody reads.

                    UNTIL THAT SWITCH IS FLIPPED, THE LIVE SITE IS STILL THE
                    UNOPTIMISED SOURCE TREE. Every number in this report is
                    from the production build, served locally over h2+gzip on
                    a harness calibrated against the live site. Final
                    acceptance against the deployed URL is one settings
                    change and one push away, and has not been done.
